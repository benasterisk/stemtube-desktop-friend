# Plan de migration — Back-port des améliorations StemTube Desktop Friend → Server R2

## 1. Contexte & objectif

Ce document décrit le back-port des améliorations apportées par l'édition **StemTube Desktop Friend** vers **StemTube Server R2**. Friend a évolué comme un shell desktop mono-utilisateur (dérivé du POC) et a accumulé des gains réels sur quatre axes : le **mixer et son apparence** (correctifs client, polish CSS, bake du métronome à l'export), la **détection d'accords** (détecteur madmom enrichi, mapping temps-réel→grille synthétique), le **karaoké et les pop-ups paroles**, et surtout le **métronome / détection de beat / precount** (moteur POC serveur complet + upgrade client de `jam-metronome.js` avec offset manuel, Tap-to-Sync et nudge). L'objectif est d'importer ces améliorations dans R2 **sans casser aucune des fonctions serveur propres à R2** : multi-utilisateur, droits, bibliothèque perso + partagée, module admin (extraction/suppression), rafraîchissement des cookies YouTube, sessions jam temps réel, et vue mobile PWA. Le métronome/precount est la pièce maîtresse du chantier et concentre à la fois le plus de valeur et le plus de risque de couplage (schéma DB partagé, split global/user, dépendances jam et mobile).

## 2. Cartographie des repos

| Rôle | Repo | Nature |
|---|---|---|
| **Source** (améliorations) | `github.com/benasterisk/stemtube-desktop-friend` | Édition desktop mono-utilisateur, dérivée du POC. `app.py` « desktop only » (`ensure_desktop_user`, auto-login), pas de multi-user, pas de mobile, pas de jam. **Hors scope** : le packaging Windows/Linux de R2 (installeurs) n'est PAS traité ici. Le bloc « compiled-mode » (PyInstaller/Nuitka) présent dans certains fichiers Friend est inerte côté serveur (`sys.frozen` faux) et est porté tel quel sans action de packaging.

### 3.5 Mobile

Aucune amélioration Friend dans ce domaine (Friend n'a pas de vue mobile). La vue mobile est **exclusivement R2** et constitue une zone à protéger, pas à porter. ## 6. Points ouverts / à décider

1. **Sous-projet métronome mobile (risque plus élevé)** — `jam-metronome.js` et `chord-display.js` sont chargés par `mobile-index.html`/`mobile-app.js`. `mobile-app.js` construit `JamMetronome` séparément (~3288) sans `manualOffsetSec` ni listener `metronomeOffsetChanged` : sans câblage explicite, le mobile perd silencieusement la persistance de l'offset. Décider si le mobile reçoit tap-sync/offset dans le même chantier ou en phase ultérieure. Les overrides `mobile-audio-patch.js`/`mobile-touch-fix.js` patchent les mêmes méthodes core → re-valider à chaque port audio-engine.

2. **Une seule voie mixer** — Friend embarque DEUX fronts mixer (`static/js/poc/*` chargé par son `mixer.html`, ET le legacy `static/js/mixer/*` + `jam-metronome.js`). R2 n'utilise que `mixer/*` + `jam-metronome.js`. **Décision structurante** : soit exposer les capacités POC (precount/timbres) via l'UI mixer R2 existante (cherry-pick de concepts `precount.js`/`timeline.js`), soit adopter le shell POC — jamais câbler les deux sur la même page. Recommandation par défaut : garder le mixer R2 et n'importer que le backend POC exposé via l'UI R2 ; le front `static/js/poc/` devient alors optionnel.

3. **Précédence `COALESCE` de `metronome_offset_ms`** — Friend fait `COALESCE(gd, ud)` (global d'abord) ; pour un nudge per-user en R2 c'est l'inverse attendu (`COALESCE(ud, gd)`, user d'abord). Ne PAS copier aveuglément l'ordre de `beat_offset` (lui légitimement partagé car dérivé de l'analyse). À trancher : autorise-t-on un admin à fixer un défaut partagé (`global_downloads`) distinct du nudge perso ?

4. **Endpoint `/metronome-offset` multi-user** — Friend écrit `global_downloads` inconditionnellement (mono-user, inoffensif là-bas ; **catastrophique en R2**). La réécriture per-user est non négociable ; reste à décider si l'on stocke dans `user_downloads` ou dans une table d'overrides par-user dédiée.

5. **Disque & concurrence du cache POC** — le moteur écrit des WAV à la demande (metronome/precount/stop/par-instrument). En multi-user : quota/cleanup nécessaires sous `.poc_cache` (le `_gc_exports` de Friend ne GC que les dirs d'export temp, pas le cache par-instrument). `detect_intro`/`set_metro_instrument` re-bakent et mutent `meta.json` → risque de race sur des requêtes concurrentes (deux users, ou un user deux onglets) que l'hypothèse mono-user de Friend ne protège pas.

6. **Réconciliation CSS accords mobile** — le namespace `.mobile-chord-*` prepend dans `chords.css` (Friend) peut dupliquer ou entrer en conflit avec la vue accords mobile PWA existante de R2 (`css/mobile/`, `mobile-index.html`). Vérifier avant tout append que le JS émettant le markup `.mobile-chord-*` est présent, sinon styles morts.

7. **`lyrics-popup.css` — skip confirmé ?** — refactor cosmétique de valeur nulle (extraction verbatim de blocs déjà inline dans `layout.css` R2). Recommandation : ne pas porter. À confirmer explicitement pour clore le point.

8. **Colonne `metronome_offset_ms` sur DB existantes** — confirmer que la migration ALTER/CREATE additive de R2 s'applique bien aux bases déjà déployées (Hetzner) sans casser le split deux-tables ni les exports `user_views`/`admin`.

9. **Attribution CC0 des samples** — le docstring de `click_kit.py` prétend « no third-party samples », mais `CREDITS.txt` liste 8 percussions Freesound CC0. Repo R2 public → livrer `CREDITS.txt` et corriger/ignorer le docstring trompeur.
